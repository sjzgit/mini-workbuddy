# 聊天页面

1. 开发聊天功能，用户可以选择 Agent 进行多轮对话，会话和聊天记录保存到数据库，刷新页面或重新打开后可以继续聊天。
2. 注意：本阶段只实现模型直接回答，不调用工具、不启动 MCP Server，也不加载 Skills。

## 页面布局

1. 聊天页面分为左右两部分：
- 左侧会话列表：展示已保存的会话，顶部提供“新建会话”按钮。
- 右侧聊天区域：
  - 顶部：会话标题
  - 中间是聊天区域：展示聊天记录
    - 用户消息靠右，Agent 回复靠左。页面配色、字号和交互方式与已有管理页面保持一致。
    - Agent回复的消息顶部要显示对应Agent名称，这样可以做切换后知道这个消息是哪个Agent回复的
    - Agent回复的消息支持：复制、重新生成（仅最后一条消息可以重新生成）
    - 消息内容前端需要使用 markdown 插件展示
  - 底部是用户输入区域：
    - 提供多行输入框、发送按钮，以及生成过程中的停止按钮
    - 底部支持选择Agent，也支持快捷 `@` 唤起Agent选择，每次输入都是与当前选择的Agent对话
    - 新建会话默认选择`默认Agent`。没有可用 Agent 时，提示用户先创建 Agent，提供前往 Agent 管理的入口，并禁用发送。

## 会话管理

1. 新建会话时，将会话保存到后端，保存成功后加入列表并自动选中，初始标题为“新会话”。
2. 第一条用户消息保存成功后，截取适当长度作为会话标题，不额外调用模型生成标题。
3. 会话列表展示标题和最后更新时间，按最后更新时间倒序排列。产生新消息时更新会话时间，仅查看会话不改变排序。
4. 点击会话后，加载对应的聊天记录。列表接口只返回会话摘要，不提前加载所有会话的完整消息。
5. 会话保存当前选择的 Agent，再次打开时恢复选择。本阶段不开发会话删除功能。

## 发送消息与流式回复

1. 输入框使用回车发送，Shift + Enter 换行。中文输入法处于选词或组字状态时，回车不得触发发送。空内容或仅包含空白字符时不能发送。
2. 用户发送消息后，先保存用户消息。保存成功后清空输入框，并显示“正在思考”；保存失败时保留输入内容，提示原因，不继续请求模型。
3. 后端读取所选 Agent 的模型配置和系统提示词，发起真实模型请求。模型调用和密钥读取必须在后端完成，前端不得获取 API Key。后端日志中需要实时打印出调用第三方大模型的API请求响应日志
4. 收到正文后显示“正在生成”，并随模型输出流式追加内容，不能等全部生成后一次性展示。流式内容需要保持顺序，避免重复或丢失。这里需要分别显示思考过程和回答内容。
5. 回复完成后，将完整消息内容保存到数据库，结束生成状态。保存失败时明确提示，不得让用户误以为回复已经可靠保存。

## 多轮对话

1. 每次请求模型时，携带当前 Agent 的系统提示词，以及当前会话按顺序排列的有效历史消息，让模型能够理解连续追问。
2. 本次用户消息已经保存到数据库，构造上下文时只加入一次，不能重复追加。
不同会话的历史必须相互隔离，不能混入其他会话的消息。失败或取消产生的未完成回复，不作为完整回答加入后续上下文，错误提示也不作为聊天内容发送给模型。
3. 本阶段不做自动摘要或上下文压缩。历史过长、超过模型可用上下文容量时，明确提示用户缩短输入或新建会话，不得静默丢弃历史。

## 聊天记录保存

1. 会话和聊天记录使用现有数据库持久化，不使用 JSON 文件或浏览器本地存储代替。
2. 每条消息保存所属会话、Agent、正文、创建时间和完成状态，并使用稳定的顺序字段读取，不能仅依赖时间戳排序。
3. Agent 回复保留生成时的 Agent 标识和名称。后续切换、改名或删除 Agent，不改变旧回复显示的归属。
4.刷新页面或重新打开后，能够加载会话列表（自动滚动到底部），查看原来的聊天记录，并继续发送消息。未完成的回复需要显示真实状态，不能当作正常完成的回答。

## 切换 Agent
1. 同一个会话允许切换 Agent，切换只影响后续请求。
2. 后续请求使用新 Agent 的模型和系统提示词，同时保留当前会话的有效聊天历史，不沿用旧 Agent 的系统提示词。
3. 会话原来选择的 Agent 已被删除或不可用时，仍可查看聊天记录，但继续发送前需要选择可用 Agent。

## 生成状态与停止

1. 当前会话正在生成时，禁止重复发送和切换 Agent。请求完成、失败或取消后，恢复操作。
2. 用户点击“停止生成”时，前端停止接收输出，后端尽可能终止模型请求并清理资源。
3. 支持后台继续生成。生成期间切换会话、新建会话或离开聊天页面时，后台需要继续生成回答。

## 异常处理

1. 处理模型连接失败、请求超时、返回空内容和流式输出中断等情况，以便于理解的独立提示展示原因，不得将错误提示保存成 Agent 回答。
2. 失败或取消时，保留已经保存的用户消息。如果已生成部分正文，则保存并标记为未完成；没有正文时，不创建空白回复。
3. 无论在哪个阶段失败，都需要结束等待状态，让用户可以继续操作。错误信息和日志不得泄露 API Key 等敏感信息。
