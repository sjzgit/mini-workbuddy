# User Workspace & Filesystem Permission

你现在是本项目的主力 AI Coding Agent。

请在当前代码库中实现一个完整的生产级功能：

> **User Workspace & Filesystem Permission**
>
> 允许用户在 Chat Session 中选择当前 Workspace，并让 `file_read_write` / `shell` 工具基于统一的 Workspace Permission 机制访问文件系统。

---

# 一、开发目标

当前系统的文件读写和 Shell 执行只能使用系统配置的默认授权目录。

现在需要增加：

> **User-selected Session Workspace**

用户可以在 Chat 输入区域选择一个目录作为当前 Session 的 Workspace。

例如：

```text
System Workspace:
D:\mini-agent-data

Session Workspace:
D:\projects\my-project
```

那么当前 Session 中：

```text
D:\mini-agent-data
D:\projects\my-project
```

属于允许访问范围。

如果 Agent 尝试访问：

```text
D:\projects\other-project
```

则不能直接执行，而应该进入：

```text
ASK_USER
```

等待用户确认。

如果用户允许：

> 当前消息 / 当前 AgentRun 临时允许访问该路径。

如果用户拒绝：

> 本次操作 DENY。

# 四、核心概念

本功能必须明确区分以下三个概念。

## 4.1 System Workspace

系统管理员 / 系统配置指定的默认授权目录。

例如：

```text
D:\mini-agent-data
```

所有 Session 默认都可以访问。

---

## 4.2 Session Workspace

用户在当前 Chat Session 中主动选择的 Workspace。

例如：

```text
D:\projects\demo
```

它属于：

```text
Session
```

而不是：

```text
Agent
```

必须支持：

```text
Agent
 ├── Session A → Workspace A
 ├── Session B → Workspace B
 └── Session C → Workspace C
```

不同 Session 可以拥有不同 Workspace。

---

## 4.3 Temporary Grant

当 Agent 请求访问 Workspace 之外的目录时：

```text
PermissionChecker
        ↓
ASK_USER
        ↓
用户允许
        ↓
Temporary Grant
```

Temporary Grant 只针对：

```text
当前 AgentRun / 当前消息
```

生效。

不能因为用户允许过一次，就永久修改 Session Workspace 或系统 Workspace。

下一条用户消息再次访问该目录时：

> 必须重新检查权限。

# 五、Workspace 数据模型

如果项目已有 Session 数据结构，请在现有结构上扩展。

推荐概念：

```text
Session
├── id
├── ...
└── workspace
      ├── path
      ├── source
      └── selected_at
```

其中：

```text
source:
SYSTEM
USER_SELECTED
```

但不要机械复制该结构。

如果项目现有数据模型有更合适的表示方式，优先遵循项目已有设计。

---

# 六、Workspace 必须是 Session Scope

这是本功能的核心架构约束。

Workspace：

```text
Session-scoped
```

不能设计成：

```text
Agent-scoped
```

例如：

```text
Agent = CodingAgent

Session A
Workspace = D:\project-a

Session B
Workspace = D:\project-b
```

两者互不影响。

---

# 七、Workspace 修改只影响后续消息

例如：

```text
10:00
Session Workspace = project-a

10:01
用户执行消息 A
```

此时使用：

```text
project-a
```

然后用户切换：

```text
10:02
Session Workspace = project-b
```

之后：

```text
10:03
用户执行消息 B
```

使用：

```text
project-b
```

历史消息和已经执行完成的 AgentRun：

> 不应该被 retroactively 修改。

# 十、WorkspaceManager

增加统一的 Workspace 管理抽象。

概念：

```python
class WorkspaceManager:
    def get_workspace(session_id):
        ...

    def set_workspace(session_id, path):
        ...

    def clear_workspace(session_id):
        ...
```

WorkspaceManager 负责：

- 获取 Session Workspace
- 设置 Session Workspace
- 清除 Session Workspace
- 校验 Workspace 路径
- 持久化 Workspace 状态
- 与 Session 生命周期关联

不要让：

```text
file_read_write
shell
AgentRuntime
Frontend
```

各自读取和修改 Workspace。

# 十一、PermissionManager

权限判断必须集中管理。

建议：

```text
WorkspaceManager
        ↓
PermissionManager
```

或者根据现有架构形成：

```text
WorkspaceManager
WorkspaceResolver
PermissionManager
```

核心 API 概念：

```python
decision = permission_manager.check(
    path=path,
    session=session,
    execution_context=context
)
```

返回：

```text
ALLOW
ASK_USER
DENY
```

绝对不要只返回：

```text
True / False
```

因为：

```text
False
```

无法区分：

```text
ASK_USER
```

和：

```text
DENY
```

---

# 十二、权限规则

最终授权目录：

```text
Authorized Paths
=
System Workspace
+
Session Workspace
+
Temporary Grants
```

访问判断：

```text
请求路径
    ↓
Path Resolver
    ↓
Canonical Path
    ↓
PermissionManager
    ↓
┌──────────────┬──────────────┬──────────────┐
│    ALLOW     │  ASK_USER    │     DENY     │
└──────────────┴──────────────┴──────────────┘
```

---

# 十三、Path Resolver

这是本功能非常重要的一部分。

禁止使用简单字符串前缀判断：

```python
path.startswith(workspace)
```

这种方式是不安全的。

例如：

```text
D:\project
D:\project-secret
```

字符串前缀可能产生误判。

同时必须处理：

```text
..
.
绝对路径
相对路径
符号链接
Windows Path
UNC Path
大小写
路径分隔符
```

例如：

```text
D:\project\src\..\secret.txt
```

应该先 canonicalize。

---

# 十四、路径判断

最终应该比较：

```text
Canonical Requested Path
```

和：

```text
Canonical Authorized Root
```

逻辑应该是：

```text
requested_path == authorized_root
```

或者：

```text
requested_path 在 authorized_root 目录树内
```

而不是简单：

```text
string prefix
```

---

# 十五、必须处理 Symlink

这是一个重要安全边界。

例如：

```text
D:\project\link
```

实际上指向：

```text
D:\secret
```

如果：

```text
D:\project
```

是 Workspace，

那么：

```text
D:\project\link\secret.txt
```

不能仅仅因为字符串位于：

```text
D:\project
```

下面就直接允许。

需要根据当前运行环境采用适当的：

```text
resolve
realpath
canonical path
```

策略。

测试必须覆盖 Symlink / Junction 等当前平台适用情况。

---

# 十六、System Sensitive Paths

设计一个系统敏感目录策略。

例如：

```text
系统关键目录
用户凭据目录
SSH credentials
系统配置目录
其他明确禁止访问的路径
```

即使：

```text
PermissionManager → ASK_USER
```

也不应该允许用户通过确认绕过系统级 DENY。

也就是说：

```text
System Protected Path
        ↓
DENY
```

而不是：

```text
ASK_USER
```

具体敏感目录列表必须结合当前运行平台和项目已有安全配置。

不要硬编码一个不适用于项目部署环境的巨大黑名单。

更推荐：

```text
Policy / Configuration
```

提供扩展能力。

# 十七、file_read_write 接入

当前：

```text
file_read_write
```

所有涉及 filesystem 的操作都必须经过 PermissionManager。

包括但不限于：

```text
read
write
create
delete
rename
move
copy
list
mkdir
```

如果当前工具支持这些操作，都必须统一检查。

不能只检查：

```text
read
```

而：

```text
delete
```

绕过权限系统。

---

# 十八、不要让 LLM 自己判断权限

非常重要：

错误方式：

```text
LLM：
这个路径应该可以访问。
```

或者：

```text
LLM：
我觉得需要问用户。
```

正确架构：

```text
LLM
 ↓
Tool Call
 ↓
Tool Runtime
 ↓
PermissionManager
 ↓
ALLOW / ASK_USER / DENY
```

权限属于：

> Runtime / Security Layer

而不是：

> Prompt Layer

---

# 十九、Shell 接入

Shell 比 file_read_write 更危险。

当前 Shell 如果是：

```text
Host subprocess
```

必须接入统一 PermissionManager。

但要明确：

> **应用层 PermissionChecker 不能等同于真正的 Sandbox。**

例如用户 Workspace：

```text
D:\project
```

Agent 执行：

```bash
python evil.py
```

而：

```python
evil.py
```

内部执行：

```python
open("D:/secret/file.txt")
```

仅检查 Shell command 中出现的路径，是无法可靠解决这个问题的。

因此本 Phase：

### 必须实现

```text
Shell Tool
    ↓
PermissionManager
```

对于能够明确解析出的：

```text
cwd
文件路径参数
```

进行权限检查。

### 但是

不要声称：

> 现在已经实现完整 Shell Sandbox。

应该明确保留未来：

```text
SandboxManager
DockerSandbox
OS Sandbox
VM Sandbox
```

的扩展接口。

# 二十、ExecutionContext

为了后续向 Harness / Sandbox 演进，建议让 Tool 执行逐步使用：

```python
ExecutionContext
```

概念：

```text
ExecutionContext
├── session
├── workspace
├── memory
├── tool_permissions
├── temporary_grants
├── runtime_config
└── trace
```

Tool：

```python
tool.execute(
    input,
    execution_context
)
```

不要让每个 Tool 自己：

```text
查询数据库
获取 Session
获取 Workspace
获取 User
判断权限
```

这些应该由 Runtime Context 统一提供。

如果当前项目还没有 ExecutionContext：

> 可以先建立最小版本，但不要因此重构整个 Runtime。

# 二十一、Ask User 流程

如果当前项目已经有 Ask User / Human-in-the-loop：

> 必须复用现有机制。

如果没有，则实现一个与 Runtime 状态机兼容的最小机制。

核心流程：

```text
Agent
 ↓
Tool Call
 ↓
PermissionManager
 ↓
ASK_USER
 ↓
AgentRun / ToolExecution Paused
 ↓
发送 Ask User
 ↓
用户选择
 ├── Allow
 │      ↓
 │  Temporary Grant
 │      ↓
 │  Resume
 │
 └── Reject
        ↓
      DENY
        ↓
      Tool Error
        ↓
      Agent Continue
```

不要：

```text
ASK_USER
 ↓
永久修改 Workspace
```

---

# 二十二、Ask User 的授权范围

MVP 默认：

```text
Current AgentRun
```

即：

```text
用户允许
→ 当前 AgentRun 可以继续访问
```

下一条消息：

```text
重新检查
```

例如：

```text
Message A
访问 D:\project-b
→ ASK
→ Allow
→ Message A 可以访问

Message B
访问 D:\project-b
→ 再次 ASK
```

# 二十八、并发 / Race Condition

考虑：

```text
Session Workspace = A

AgentRun 1 正在执行

用户切换 Workspace = B

AgentRun 1
```

AgentRun 1 不应该因为 Session 当前 Workspace 变化而中途突然从：

```text
A
```

切换成：

```text
B
```

因此建议：

> AgentRun 开始时 snapshot 当前 Workspace / Capability Context。

即：

```text
Session
   ↓
AgentRun Start
   ↓
Workspace Snapshot
   ↓
ExecutionContext
```

之后：

```text
Session Workspace 改变
```

只影响：

```text
Future AgentRuns
```

不会修改：

```text
Running AgentRun
```

这是非常重要的架构不变量。

# 三十二、架构不变量

完成后必须保证：

### Invariant 1

Workspace 是：

```text
Session-scoped
```

不是 Agent-scoped。

### Invariant 2

权限判断只能来自：

```text
PermissionManager
```

不能散落在 Tool 中。

### Invariant 3

LLM 不负责安全权限判断。

### Invariant 4

Permission decision 必须至少有：

```text
ALLOW
ASK_USER
DENY
```

### Invariant 5

Temporary Grant 不得永久改变 Workspace。

### Invariant 6

Workspace 修改不影响已经启动的 AgentRun。

### Invariant 7

路径判断不能使用简单字符串前缀。

### Invariant 8

系统保护目录不能通过 Ask User 绕过。

### Invariant 9

file_read_write 和 shell 必须使用统一 Permission Layer。

### Invariant 10

# 最终要求

这是一个生产级 Agent Runtime 的基础能力。

请不要采用“能跑就行”的实现。

重点保证：

```text
Session Workspace
        ↓
Permission
        ↓
Ask User
        ↓
Tool Execution
```

这一条链路的职责清晰、状态一致、权限集中、可测试、可审计，并且为未来 Sandbox / Harness Architecture 留出扩展空间。

同时遵循当前项目已有代码风格、目录结构、命名规范、异常处理、API 风格和测试规范。

**先分析代码库 → 输出实施计划 → 再实施 → 测试 → 最终汇报。**
